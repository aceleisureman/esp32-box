Hardware · 选型

为什么必须是 ESP32-S3

不是「性能更好」这么笼统 —— 是三个功能没它就实现不了

向量指令扩展

决定唤醒词能否跑起来。esp-sr 的 WakeNet9 是神经网络模型，S3 的 SIMD 指令为其提供硬件加速。ESP32 / C3 无此扩展，同模型延迟不可接受。

8MB Octal PSRAM

决定音频缓冲能否开够。256KB 流缓冲 + 512KB PCM 环形缓冲 + 模型驻留，全部走 ps_malloc。内部 SRAM 只有 512KB，装不下。

双核 240MHz

决定 UI 会不会卡。音频解码钉在 core 0，Arduino loop（UI）钉在 core 1。单核架构下 FLAC 解码会把屏幕刷新挤没。

代码里的硬门槛：没有 PSRAM 就不启用唤醒词

void WakeWordClass::init() {
    if (!psramFound()) {
        _enabled = false;
        Serial.println("[WAKE] PSRAM unavailable; wake word disabled");
        return;   // 与其运行中 OOM 崩溃，不如启动就明确关闭
    }
    // 优先级 3 高于音频任务，钉在 core 1 与 UI 同核 —— 唤醒检测必须实时
    xTaskCreatePinnedToCore(taskEntry, "wake", 12288, this, 3, &_task, 1);
}

Arduino 与 ESP-IDF 混合框架

屏幕库和音频库在 Arduino 生态，唤醒词库在 IDF 生态 —— 两个都要

✗ 问题

纯 framework = arduino 时，PlatformIO 不会编译 components/ 下的 IDF 组件。esp-sr 静静躺在目录里，链接阶段报满屏 undefined reference。

但 Adafruit GFX / ST7789、ESP8266Audio、WebSockets、ArduinoJson —— 项目主体全在 Arduino 生态，不可能推倒重来。

✓ 解法：两个框架同时启用

; platformio.ini
framework = arduino, espidf

; src/CMakeLists.txt —— Arduino 核心被注册为 IDF 组件
idf_component_register(SRCS ${app_sources}
  REQUIRES framework-arduinoespressif32 bt esp-sr)

IDF 构建系统接管全局，Arduino 核心以组件身份被依赖 —— setup() / loop() 照常可用。

顺带解掉 -Werror

esp-sr 源码带有 format-truncation / maybe-uninitialized 告警。严格模式下第三方库的告警会让整个项目构建失败 —— 不是自己的代码，只能豁免。

版本锁定的教训

ESP8266Audio 固定 1.9.7：git 主分支已改用 IDF 5.x 的 driver/i2s_std.h，而 arduino-esp32 v2.0.17 基于 IDF 4.4，只有旧版 driver/i2s.h。不锁版本，某天 CI 会突然红。

关键处理：24bit 装在 32bit 槽里，还要额外放大 4 倍

// INMP441 输出 24-bit 有效数据，承载在 32-bit I2S 时隙中。
// 直接按 16-bit 读取会落在无效低位，表现为持续全零。
cfg.bits_per_sample = I2S_BITS_PER_SAMPLE_32BIT;

for (int i = 0; i < count; ++i) {
    int32_t s = raw[i] >> 11;      // 取 24bit 有效位
    s *= 4;                      // 实测幅度偏低，再放大
    if (s > 32767) s = 32767;   // 饱和截断，防溢出回绕
    else if (s < -32768) s = -32768;
    samples[i] = (int16_t)s;
}

数据源WebSocket 推送，长度未知

缓冲512KB 环形缓冲（PSRAM）
输出24kHz 直出

预缓冲 100ms：拿延迟换连续

收到第一个 PCM 包就播 → WiFi 抖动导致第二包晚到 → 声音断一下。先攒 kPcmPrebufferMs = 100 再起播，用 100ms 延迟换整段回复不卡。

⚠ 为什么 TTS 播完不能报「结束」

主循环靠 finished 事件自动切下一首。若 TTS 播完也置位 → 用户问完一个问题，歌莫名其妙换了一首。

提示音也在 PSRAM 里：880Hz 正弦波 200ms，开机时用 ps_malloc 合成一段完整 WAV（含 44 字节头）常驻内存，之后每次「叮」都复用同一份 —— 零网络依赖、零文件读取。

Debug · 因果链

歌词一滚动，喇叭就「刺啦」

屏幕和喇叭之间没有任何直接关系 —— 但它们共用同一套 Flash 缓存

现象：歌词滚动时出现爆音，歌词静止时声音完全正常

直觉方向全是错的 —— 电源纹波？接地回流？SPI 与 I2S 抢总线？都不是。

① 绘制
渲染一个汉字
② 读取
从 SPIFFS 取字形
③ 副作用
两个核的 Flash 缓存被暂停
④ 波及
跑在 flash 里的解码代码停摆
⑤ 现象
I2S 欠载 → 爆音

✓ 解法：字库全量驻留 PSRAM

开机时一次性把整个字库读进 PSRAM，之后绘制路径完全不碰 Flash。

16px 字库485 KB3817 字
32px 字库1.87 MB8MB PSRAM 装得下
索引表7.5 KB常驻，优先 PSRAM

附带坑：一次 read 近 2MB 在部分 SPIFFS 实现上会失败 —— 大块读取必须分片进行。

Backend · 架构

后端就是一根双向管道

两个 WebSocket，两个线程，中间做协议翻译

为什么必须双线程

两个方向完全独立：用户正在说话的同时，上一轮回复音频可能还在下发。单线程轮询会互相阻塞。

_device_to_upstream
收设备音频帧 → base64 → 上游
_upstream_to_device
收上游事件 → 翻译 → 设备

三个并发细节

共用 stop 事件 任何一边退出立刻 _stop.set()，另一边同步收敛 —— 不留半死连接
发送加锁 _device_send_lock 保护 —— WebSocket send 非线程安全，并发写会撕碎帧
线程回收超时 join(timeout=2.0)，超时未退出直接抛错，不允许线程泄漏
⚠ 正常断开 ≠ 异常断开 
# Flask-Sock 1000/1001 close is a normal device lifecycle event.
return name == "ConnectionClosed" and code in (1000, 1001)

设备关机 / 用户退出属正常生命周期。不区分 → 日志全是「异常」，真问题被淹没。

假设设备发来的都是垃圾

嵌入式设备会发畸形数据 —— 服务器不能因为一个坏帧就倒下

上行音频帧的三重校验

校验错误码为什么这样定
非空empty_audio_frame空帧无意义，往上游发只会污染 VAD 判断
≤ 4096 字节audio_frame_too_large设备正常帧是 640B。超大帧说明设备侧缓冲已经错乱
偶数字节unaligned_audio_framePCM16 一个采样 = 2 字节。奇数长度 = 帧边界错位，继续处理只会产生噪音

✓ 关键：拒绝，但不断开

if len(frame) % 2:
    self._send_device_json({
        "type": "protocol_error",
        "code": "unaligned_audio_frame",
        "message": "PCM16 音频帧必须是偶数字节",
    })
    continue      # 跳过这一帧，会话继续

断开连接 = 用户感受到「突然不能用了」。
跳过一个坏帧 = 用户完全无感。

上游数据同样不可信

invalid_audio_base64上游音频不是有效 Base64
invalid_upstream_json上游文本帧不是 JSON
invalid_upstream_event事件不是 JSON 对象
unsupported_event设备发来未知事件类型

Takeaway · 方法论

三条我认为最值钱的经验

比任何具体技术点都更通用

01 注释写「为什么」

代码本身已经说明「做了什么」。只有注释能说明「为什么这么做」「不这样会出什么事」。

✗ 「设置采样率为 16000」
✓ 「按 16-bit 读取会落在无效低位，表现为持续全零」

本期引用的每一条注释都属于后者 —— 它们是这期视频的全部素材来源。

02 不变量要落纸落测试

跨模块的约束不能只存在于脑子里 —— 半年后回来改，或者别人接手，它一定会被无意破坏。

「任何模块在前一个持有者确认释放之前，都不得安装麦克风驱动」
→ 写进设计文档
→ 写成后端契约测试

测试锁住的不是代码行为，是当初那个决策的理由。

03 可观测性提前埋

嵌入式没有断点调试的奢侈，串口日志就是你的全部视野。出问题再加日志，往往已经复现不了。

· 内存最大连续块（不只是剩余量）
· 任务栈高水位线
· 麦克风 RMS / peak / 削顶计数

碎片化时，「剩余总量」和「最大连续块」会严重背离 —— 只看总量会误判。
